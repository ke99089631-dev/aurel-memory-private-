# 2026-11-11 (火) episodic

## 18:40 会長の気づき「touch2sbちゃんと繋がってるのか？異常にエントリーがない」→ 的中・原因確定

### 結論
- **畑A(US100・farm_a_exec)は正常**。5分ごとに接続・NY帯で発火(直近=11-11 02:52 JST SELL→SL -1.0R)。16発/14営業日。今日のNY帯はまだ(23:30 JST〜)。
- **ゴールド2タッチデモ(demo_exec・MT5Demo 802307)は11-01以降、発火を全部黙って捨てていた**。プロセスは生きていて state も毎20秒更新=監視上は「健康」。台帳(demo_exec_ledger)の最終行は10-28 09:20。

### 原因(確定)
1. `mt5_bridge.py` の `SERVER_UTC_OFFSET_H = 3` が固定値。業者サーバは **2026-11-01(米国夏時間終了)で GMT+3→GMT+2** に移行。
2. 以後、8793の /api/data が返す足の時刻ラベルが**実時刻より1時間古い**(18:41 JST時点: 最新確定足ラベル 08:40 UTC、実時刻 09:41 UTC)。
3. setup_engine→touch2sb_ledger の `entry_time` も1時間古い(logged_at との差 ≈3600秒。10-28までは数秒)。
4. demo_exec の鮮度フィルタ `FRESH_SEC=180` が全発火を「古い」と判定→ `[skip]` を print するだけ(pythonw=標準出力なし)・台帳に書かず・seen に登録。
5. **落とした発火 8本**: 11-05 ×4 / 11-06 ×1 / 11-09 ×3 (T2-1793841300 … T2-1794191100)。
6. 副作用: 会長フィルタ(JST 07–12時)が実時刻 08–13時に1時間ずれて評価されていた(発火の生成自体も11-01以降1時間ずれ)。チャートの時刻表示・ピンバー票・15m車線も同じ足を読むので同じずれ。

### 直し方(提案・未適用)
- `mt5_bridge.py` のオフセットを固定値でなく **サーバ時刻−システムUTCから毎回算出**(または米国DSTルール: 3月第2日曜〜11月第1日曜=+3、それ以外=+2)。
- demo_exec の `[skip]` を台帳行(kind=skip)として残す=黙って捨てない。
- 反映には 8793 (AUREL_ChartServe) 再起動が要る。setup_engine/demo_exec は API を読むだけなので再起動不要の見込み。
- 11-01〜今日のゴールド2タッチの紙/デモ記録は時刻1時間ずれ付きとして扱う(除外か注記)。

### 教訓
- 「プロセス生存」≠「車線生存」。上流の発火数と下流の記録数を毎日突合する健康チェックが要る。
- 捨てる判断は必ず台帳に残す。
- 夏時間切替週(3月末/10月末/11月第1日曜)はブリーフで注意喚起。
